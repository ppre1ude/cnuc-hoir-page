# 가입 승인 알림 설계

작성일: 2026-11-03. 대상: 단원 레이아웃과 운영진 레이아웃, `features/member/`의 새 알림 띠, `lib/api.ts`의 쓰기 완료 알림. 서버는 바꾸지 않는다.

## 왜 바꾸는가

가입 신청이 들어와도 운영진은 알 길이 없다. 신청은 가입 승인 화면(`/admin/applications`)이나 단원 정보 관리 화면의 승인 대기 행에 들어가야만 보인다. 2026-11-03 사용자 확인: 운영진은 보통 홈에 있고, 운영진 화면에 들어가도 첫 화면만 보고 있어서 신청이 들어온 줄 몰랐다. 승인이 늦어지면 새 단원이 포털을 쓰지 못하고, 승인이 빠를수록 접속자가 늘어나는 상황이라 세 항목 중 가장 급하다.

## 결정한 것

### 누가, 어디서 보는가

- 가입 승인 권한(`APPROVE_APPLICATIONS`)이 있는 운영진에게만 보인다. 판단은 `can(session, "APPROVE_APPLICATIONS")` 하나로 한다. 다른 단원과 권한 없는 운영진에게는 아무것도 그리지 않는다.
- 로그인 뒤 모든 화면에서 같은 자리에 보인다. 단원 화면(홈, 공지, 내 출석, 자료실, 일정 상세)은 헤더 바로 아래, 운영진 화면은 하위 메뉴 바로 아래다. 두 레이아웃(`(member)/layout.tsx`, `(admin)/layout.tsx`)이 같은 컴포넌트를 메뉴 다음, 본문 앞에 둔다.
- 세 경로에서는 숨긴다. 가입 승인 화면(`/admin/applications`)은 이미 그 화면에 있어서다. 현장 출석(`/events/[id]/check-in`)과 출석 관리(`/admin/events/[id]/attendance`)는 연습장에서 휴대폰으로 급히 쓰는 화면이라 띠가 출석 코드 입력과 출석 창 열기를 아래로 밀면 안 되기 때문이다(빌더 검토 뒤 설계자 판단). 그 밖의 경로는 모두 보인다.
- 승인 대기가 0명이면 띠 자체가 없다. 대기 수를 아직 받지 못했거나 받기에 실패했을 때도 그리지 않는다. 스켈레톤이나 오류 문구는 두지 않는다. 띠는 있으면 보이고 없으면 없는 것이다.

### 무엇을 말하는가

- 문구: "가입 승인을 기다리는 단원이 N명 있어요." 오른쪽에 주요 동작 버튼 모양의 링크(`ActionLink`, primary) "승인하러 가기"를 두고 `/admin/applications`로 간다.
- 모양은 홈의 "지금 출석할 수 있습니다" 띠(`EventCalendar.module.css`의 `.checkInBanner`)와 같다. 그 스타일을 공통 UI(`components/ui/ui.module.css`)로 옮겨 둘이 함께 쓴다. 새 색이나 토큰을 만들지 않는다.
- 폭은 헤더와 같은 `--layout-wide`(1240px) 하나로 고정한다. 레이아웃에 놓이는 띠는 화면마다 다른 본문 폭(홈과 운영진 화면 1240px, 공지와 내 출석 같은 읽기 화면 880px)을 알 수 없고, 헤더 아래 띠가 헤더 폭과 같으면 어느 화면에서든 어색하지 않다. 띠와 본문 제목 사이가 너무 벌어지지 않게 띠의 아래 여백을 줄인다. 정확한 값은 빌더가 정한다.
- 마크업은 `section`에 `aria-label="가입 승인 알림"`. 글은 `p` 안의 `strong` 한 문장으로, 출석 띠의 제목 줄과 같은 크기다. 모바일(760px 이하)에서는 버튼이 한 줄을 다 차지한다(출석 띠와 같은 규칙).

### 어디서 숫자를 받는가

- 새 API를 만들지 않는다. 가입 승인 화면이 쓰는 `getApplications(0)`(`GET /admin/applications?status=APPROVAL_PENDING&page=0&size=20`)의 `total`을 읽는다.
- 같은 요청을 쓰므로 `lib/api.ts`의 1분 기억이 공유된다. 띠가 받아 둔 첫 페이지가 그대로 가입 승인 화면의 첫 그림이 되어, "승인하러 가기"를 누르면 새 요청 없이 목록이 보인다. 기억에서 꺼내는 사이 스켈레톤이 한 프레임쯤 비치는 것은 허용한다. 그것까지 없애려면 동기 읽기 함수가 필요해 일이 커진다.

### 언제 다시 받는가

1. 컴포넌트가 처음 그려질 때.
2. 경로(`usePathname`)가 바뀔 때. 1분 기억 안이면 요청이 나가지 않는다.
3. 쓰기 요청이 끝났을 때(성공, 실패 모두). `lib/api.ts`는 지금도 쓰기 요청이 끝나면 `clearRequestCache()`를 부른다. 그 자리에서 함께 알리는 작은 구독 함수(`onPermissionDenied`와 같은 꼴)를 하나 더 두고, 띠가 그것을 구독해 다시 받는다. 그래서 단원 정보 관리 화면의 행에서 승인하거나 반려해도 띠가 바로 줄거나 사라진다. `/auth/`로 가는 쓰기(로그아웃 등)는 알리지 않는다. 로그아웃 직후 띠가 다시 요청하면 401을 받아 로그인 화면으로 보내는 부작용이 생기기 때문이다.
4. 탭을 열어 둔 채로는 1분마다, 그리고 숨긴 탭에서 돌아왔을 때. `lib/poll.ts`의 `pollWhileVisible(load, 60_000)`을 쓴다. 이 주기 요청만 `cache: "reload"`로 기억을 건너뛰어 실제로 1분마다 새 값을 받는다.

실패하면 조용히 넘어가고 다음 계기에 다시 받는다. 세션이 없거나 권한이 없으면 요청 자체를 보내지 않는다.

### 문서

- `docs/design-system.md` 공통 컴포넌트 절에 알림 띠 스타일이 출석 띠와 공유된다는 것을 적고, 적용 검증 기록에 이번 변경을 남긴다.
- `docs/operations.md` "행사와 출석 현장 대응"의 가입 신청자 처리 문단에, 승인 권한이 있는 운영진은 로그인하면 어느 화면에서든 띠로 대기 인원을 본다는 한 줄을 더한다.

## 하지 않는 것

- 이메일, 카카오톡 같은 바깥 알림.
- 메뉴 글자 옆 숫자 배지. 띠가 모든 화면에 있어 중복이다.
- 띠를 닫거나 숨기는 버튼. 승인하면 사라지는 것이 유일한 닫기다.
- 대기 수만 주는 새 API. 지금 API의 `total`로 충분하다.
- 서버 코드 변경.

## 빌더에게 남긴 것

- 컴포넌트 이름과 파일 위치(`features/member/` 아래 하나). 세션은 `useSessionState()`로 읽는다. 세션이 아직 없으면 그리지 않는다.
- 띠와 본문 사이 간격, 공통 스타일로 옮길 때 클래스 이름.
- 테스트. 최소한 권한 없음, 0명, N명과 링크, 숨기는 세 경로, 쓰기 완료 뒤 다시 받기(`/auth/` 쓰기는 제외), 경로 변경 뒤 다시 받기를 vitest로 확인한다.

## 확인 기준

- 승인 권한이 있는 세션으로 홈, 공지, 단원 정보 관리, 일정 관리 화면 모두 같은 자리에 띠가 보이고 가입 승인, 현장 출석, 출석 관리 화면에서는 보이지 않는다. 권한 없는 세션에서는 어디에도 없다.
- 띠의 "승인하러 가기"를 누르면 가입 승인 화면이 새 요청 없이 그려진다(기억 공유).
- 단원 정보 관리 화면의 행에서 승인하면 띠의 숫자가 바로 줄고, 마지막 사람을 승인하면 띠가 사라진다.
- 모의 API로 1440px와 390px에서 가로 넘침이 없다.
- `web`의 vitest, tsc, eslint가 통과한다.
