# 공지 열람과 작성 설계

작성일: 2026-11-03. 대상: 단원 공지 화면(`/notices`, `features/notice/NoticeList.tsx`), 운영진 공지 관리(`/admin/notices`, `features/notice/NoticeEditor.tsx`), 새 공통 컴포넌트 `Pagination`, 운영진 화면의 복제된 이전과 다음 버튼. 서버는 바꾸지 않는다.

## 왜 바꾸는가

열람: 공지 목록은 한 페이지 20개를 받지만 넘김은 "이전, 1 / 3, 다음"뿐이어서 오래된 공지로 가려면 한 장씩 넘겨야 한다. 공지를 누르면 목록이 이미 갖고 있는 본문을 다시 받아 와서 잠깐 스켈레톤이 보인다.

작성: `NoticeEditor`가 "새 공지 작성"과 "기존 공지 수정"을 한 화면의 같은 폼으로 처리한다. 왼쪽 목록을 누르면 폼이 수정 모드로 바뀌고, "새 공지"를 누르면 작성 모드로 돌아온다. 두 일이 한 폼을 나눠 쓰니 지금 무엇을 하고 있는지 헷갈리고, 게시 여부와 투표 추가가 체크박스여서 누르기 전에 무슨 일이 생기는지 보이지 않는다.

참고한 글은 https://maily.so/uiux/posts/5xrxk0p7o2v 의 페이지네이션 원칙이다. 요약하면 여섯 가지다.

1. 한 페이지에 너무 적게 담지 않는다. 웹은 높이 제한이 없다.
2. 누르는 영역은 모바일에서 44px 이상.
3. 현재 페이지는 색만이 아니라 글자와 표시로도 구분한다.
4. 페이지 번호는 최대 10개까지만 보이고, 번호 사이 간격을 둔다.
5. 이전과 다음을 글자로 둔다. 화살표만 쓰면 뜻이 흐려진다. 번호와는 간격이나 모양으로 분리한다.
6. 모바일은 현재 번호와 이전, 다음만 남긴다.

## 결정한 것

### 공통 컴포넌트 `Pagination`

- `components/ui/index.tsx`에 둔다. 입력은 `page`(0부터), `size`, `total`, `onChange(page)`, `label`(nav의 `aria-label`). `total <= size`면 아무것도 그리지 않는다.
- 데스크톱: "이전" 버튼, 페이지 번호 버튼들, "다음" 버튼. 번호는 현재 페이지를 가운데 둔 최대 7개의 연속 구간이다(전체가 7쪽 이하면 모두). 줄임표와 첫 쪽, 끝 쪽 바로가기는 두지 않는다. 합창단 공지는 몇 해를 모아도 열 쪽을 넘기 어렵다. 넘으면 그때 더한다(`ponytail` 주석으로 남긴다).
- 현재 페이지 버튼은 `aria-current="page"`에 초록 채움(primary 버튼 모양)이고 나머지는 일반 버튼 모양이다. 글자 굵기도 다르게 해 색에만 기대지 않는다.
- 이전과 다음은 번호 묶음과 `--space-4` 이상 떨어뜨리고, 번호 사이는 `--space-2`다. 모든 버튼은 `--control-medium`(44px) 높이다. 첫 쪽에서 이전, 끝 쪽에서 다음은 꺼진다.
- 모바일(760px 이하): 번호 버튼을 숨기고 그 자리에 "3 / 12" 글자를 둔다. 이전과 다음은 그대로다. 화면 읽기 프로그램에는 "12쪽 중 3쪽"으로 읽힌다.
- 쓰는 곳: 단원 공지 목록, 운영진 공지 관리 목록, 가입 승인의 신청자 목록, 사전 등록된 단원 목록. 네 곳에 복제된 이전과 다음 블록을 모두 이 컴포넌트로 바꾼다. 가입 승인과 사전 등록된 단원 목록은 주소에 페이지를 남기지 않는다.

### 단원 공지 화면 `/notices`

- 한 페이지 20개는 그대로다.
- 현재 페이지를 주소에 남긴다. `/notices?page=3`처럼 사람 기준 1부터 쓰고, 1쪽은 매개변수를 생략한다. 페이지를 바꾸면 `router.replace`로 주소를 바꾼다. 새로고침과 뒤로 가기에서 그 쪽이 유지된다. 지금의 `?notice=번호`(홈에서 공지 바로 열기)는 그대로 두고 둘을 함께 쓸 수 있다. 마지막 쪽보다 큰 `?page=`는 마지막 쪽으로 보정하고 주소도 고친다. 0 이하나 글자처럼 깨진 번호는 1쪽으로 읽고 주소에서 지운다(깨진 링크에서는 첫 쪽이 자연스럽다).
- 쪽을 바꾸면 목록 제목으로 스크롤하고 거기에 초점을 둔다. 이전과 다음은 목록 맨 아래에 있어, 그대로 두면 새 쪽의 끝에 서게 된다. 지금은 스켈레톤으로 문서가 줄었다 늘면서 우연히 위에 머물렀을 뿐이다.
- 공지를 누르면 목록이 이미 받아 둔 제목과 본문을 바로 펼친다. 상세 API(`GET /notices/{id}`)는 부르지 않는다. 투표(`NoticePoll`)만 지금처럼 따로 받아 본문 아래에 채운다.
- 상세 API는 현재 쪽에 없는 공지를 `?notice=`로 바로 열 때만 쓴다(지금의 `standalone` 경로). 이 경우의 대기와 실패 처리는 지금 그대로다.
- 펼침 패턴(제목 버튼의 `aria-expanded`, 닫을 때 제목으로 초점)과 투표 배지는 바꾸지 않는다.

### 운영진 화면 셋

지금의 `NoticeEditor`(목록과 폼이 한 화면)를 없애고 세 화면으로 나눈다. 모두 `PageGate`에 `MANAGE_EVENTS` 권한을 넘긴다.

#### 공지 관리 `/admin/notices`

- 제목 "공지 관리", 오른쪽 작업 영역에 주요 동작 링크 "새 공지 작성"(`/admin/notices/new`).
- 목록만 있다. 한 행은 제목, 상태 배지(게시는 중립, 초안은 주의 색 `attention`), 날짜(게시된 공지는 게시일, 초안은 마지막 수정일), 행 끝의 →. 행 전체가 수정 화면으로 가는 링크다. 모양은 일정 관리 목록 행과 같은 규칙(굵은 윗선, 가는 구분선, 44px 이상)이다.
- 정렬은 API 그대로다(게시일 내림차순, 초안은 게시일이 없어 맨 위).
- `Pagination`을 쓰고 현재 쪽을 `?page=`에 남긴다. 2쪽 이상에서 행 링크는 `/admin/notices/12?page=3`처럼 쪽을 싣고, 수정 화면의 "공지 관리로" 링크와 저장 뒤 돌아가는 주소도 그 쪽을 그대로 돌려준다. 브라우저 뒤로 가기뿐 아니라 링크로 돌아와도 같은 쪽이다. 쪽을 바꿀 때의 스크롤과 범위 보정은 단원 공지 화면과 같다.
- 작성이나 수정 화면에서 돌아올 때 결과 안내를 한 번 보인다. "공지를 게시했습니다.", "초안으로 저장했습니다." 안내는 `Feedback`(status)이다. 전달 방법은 빌더가 정한다(예: `?done=published` 같은 1회용 매개변수를 읽고 지움).
- 빈 목록은 "작성된 공지가 없습니다. 새 공지 작성으로 첫 공지를 올려 주세요."

#### 새 공지 작성 `/admin/notices/new`

- 위에 "공지 관리로" 돌아가기 링크(출석 관리 화면의 돌아가기와 같은 모양), 제목 "새 공지 작성".
- 폼 순서: 제목(200자), 본문(10,000자, 아래 작은 안내 "주소를 적으면 단원 화면에서 링크가 됩니다."), 투표, 버튼 둘.
- 투표는 체크박스와 형식 선택을 합친 버튼 묶음 하나다. 선택지는 "없음", "참석 / 불참", "찬성 / 반대", "직접 입력"이고 기본은 "없음"이다. 가입 승인의 단원 구분 버튼과 같은 패턴(`role="group"`, 각 버튼 `aria-pressed`)이다. "없음"이 아니면 아래가 열린다. 질문(200자), 첫 번째 선택지와 두 번째 선택지(80자, 참석 / 불참과 찬성 / 반대는 미리 채우고, 직접 고치면 선택이 "직접 입력"으로 바뀜), 마감 시각(한국 시간, `datetime-local`). 지금의 안내 세 줄(질문과 선택지는 바꿀 수 없음, 응답자 이름이 운영진에게 보임, 일정 참석 응답과 무관)은 그대로 둔다.
- 게시 체크박스는 없다. 맨 아래 버튼 두 개가 게시 여부다. "초안으로 저장"(일반)과 "게시하기"(주요). 둘 다 제목과 본문이 비어 있으면 꺼진다. 투표를 켰는데 마감 시각이 비었거나 잘못되면 지금처럼 오류를 보이고 저장하지 않는다.
- 저장이 끝나면 공지 관리 목록으로 돌아가고 결과 안내가 보인다. 실패하면 이 화면에 머물며 지금의 오류 문구(`INVALID_POLL`, `POLL_EXISTS`는 서버 문구, 그 밖은 "공지를 저장하지 못했습니다.")를 보인다.
- 임시 저장은 지금 방식(`sessionStorage`의 `notice-draft`)을 유지한다. 이 화면을 열었을 때 임시 저장이 있으면 폼을 채우고 위에 "작성 중이던 공지를 되살렸습니다." 안내와 "지우기" 버튼을 둔다. 지우기는 임시 저장과 폼을 함께 비운다. 저장이 끝나면 임시 저장을 지운다.

#### 공지 수정 `/admin/notices/[id]`

- 위에 "공지 관리로" 돌아가기 링크. 제목 "공지 수정" 옆에 상태 배지(게시 또는 초안)와 게시일.
- 공지는 `GET /admin/notices/{id}`로 받는다. `notices.ts`에 `getAdminNotice(id)`를 더한다. 받는 동안은 폼 모양 스켈레톤, 404면 "공지를 찾을 수 없습니다."와 공지 관리로 가는 링크, 그 밖의 실패는 다시 시도 버튼이다.
- 제목과 본문은 작성 화면과 같은 칸이다.
- 투표가 이미 있으면 결과만 보인다. 질문, 마감 시각, 선택지별 인원, 응답자 명단. 지금 `NoticeEditor`의 투표 결과 절을 그대로 옮긴다. 투표가 없으면 작성 화면과 같은 투표 버튼 묶음으로 붙일 수 있다.
- 버튼은 둘이다. 초안이면 "저장"(일반)과 "게시하기"(주요). 게시 중이면 "저장"(주요)과 "초안으로 내리기"(일반). "저장"은 게시 여부를 그대로 두고 제목, 본문, 새 투표만 보낸다. "게시하기"와 "초안으로 내리기"도 폼에 있는 값을 함께 저장한다.
- "초안으로 내리기"는 누르면 먼저 `window.confirm`으로 묻는다. "이 공지를 초안으로 내리면 단원에게 보이지 않습니다. 다시 게시하면 게시일이 새로 정해져 목록 맨 위로 올라갑니다. 계속할까요?" 서버(`Notice.update`)가 내릴 때 게시일을 지우고 다시 올릴 때 지금 시각으로 찍기 때문이다. 반려와 OB 전환이 쓰는 확인 방식과 같다.
- 저장이 끝나면 이 화면에 머물고 "저장했습니다.", "게시했습니다.", "초안으로 내렸습니다." 안내를 보인다. 상태 배지와 버튼도 새 상태로 바뀐다. 임시 저장은 쓰지 않는다. 수정 화면에서 쓰다 끊긴 내용은 되살리지 않는다.

### 공유하는 코드

- 작성과 수정은 폼 컴포넌트 하나(`NoticeForm`)를 함께 쓴다. 입력은 모드와 초깃값, 버튼 묶음, 저장 함수다. 투표 결과 절과 투표 버튼 묶음은 작은 컴포넌트로 떼어 둔다.
- 스켈레톤은 목록용과 폼용 둘이다. 지금의 `NoticeEditorSkeleton`은 지운다.
- 탭 제목(`metadata.title`)은 "공지 관리", "새 공지 작성", "공지 수정"이다.

### 문서

- `docs/design-system.md` 공통 컴포넌트 절에 `Pagination`을 더하고 여섯 원칙 중 따른 것을 적는다. 적용 검증 기록에 이번 변경을 남긴다.
- `docs/operations.md` "공지 투표" 절 앞에 공지 작성 흐름 한 문단을 더한다. 공지 관리에서 새 공지 작성으로 들어가 초안으로 저장하거나 게시하고, 수정 화면에서 게시 여부를 바꾸며, 투표는 한 번 붙이면 바꿀 수 없다. 초안으로 내린 공지를 다시 게시하면 게시일이 새로 정해져 목록 맨 위로 올라간다는 것도 적는다.

## 하지 않는 것

- 공지 삭제, 투표 삭제와 수정. API에 없다.
- 서식 있는 본문, 첨부, 검색, 무한 스크롤, 더 보기.
- 한 페이지 개수 변경이나 개수 선택.
- 서버 API와 DB 변경.

## 빌더에게 남긴 것

- `?done=` 같은 1회용 결과 전달 방식과 `?page=`를 읽고 쓰는 공통 훅의 모양.
- `Pagination`의 번호 구간 계산과 모바일 전환 CSS.
- 테스트. 최소한 `Pagination`(구간, 현재 표시, 꺼짐, 숨김), 단원 목록의 바로 펼침과 `?page=` 유지, 공지 관리 목록과 결과 안내, 작성 화면의 두 버튼과 투표 묶음, 임시 저장 되살리기와 지우기, 수정 화면의 상태별 버튼과 404를 vitest로 확인한다. 옛 `NoticeEditor.test.tsx`는 새 화면 기준으로 다시 쓴다.

## 확인 기준

- 단원 공지에서 공지를 누르면 스켈레톤 없이 본문이 바로 펼쳐지고, 3쪽으로 넘긴 뒤 새로고침해도 3쪽이다.
- 공지 관리 3쪽에서 행을 누르면 수정 화면으로 가고, 뒤로 가기든 "공지 관리로" 링크든 저장 뒤 돌아가기든 모두 3쪽의 목록이다.
- 쪽을 바꾸면 화면이 목록 제목 위치에 있고 초점도 거기에 있다.
- 새 공지 작성에서 "게시하기"를 누르면 게시된 공지로, "초안으로 저장"을 누르면 초안으로 저장되고 목록에서 결과 안내가 보인다.
- 수정 화면에서 초안을 "게시하기"로 올리고 다시 "초안으로 내리기"로 내릴 수 있다.
- 모의 API로 1440px와 390px에서 네 화면(단원 공지, 공지 관리, 새 공지 작성, 공지 수정)의 가로 넘침이 없고, 390px에서 페이지 넘김이 "이전, 3 / 12, 다음"으로 보인다.
- `web`의 vitest, tsc, eslint가 통과한다.
