# 회원 포털 운영 준비와 절차

## 배포 전 결정

운영진에게 가입 승인 담당자와 단원 명단 대조 방법, 이메일 확인을 마친 최초 운영진 계정을 확인받아야 합니다. 메일 발송 계정·도메인과 TLS를 적용할 배포 주소도 아직 정해지지 않았습니다. 이 정보가 확정되기 전에는 실제 회원 가입과 운영 배포를 시작하지 않습니다. 공개 온보딩 디자인과 공개 행사 아카이브는 후속 범위입니다.

## 환경과 네트워크

`.env.example`은 변수 이름만 보여 주는 예시입니다. 실제 비밀번호는 저장소와 셸 기록에 남기지 않고 실행 환경의 비밀 저장소에서 공급합니다. 개발용 `compose.yaml`은 MySQL만 `127.0.0.1:3307`에 엽니다. `compose.portal.yaml`은 로컬 검증용 HTTP 프록시만 루프백에 노출합니다. API·웹·DB 포트를 외부에 직접 열지 않습니다.

| 변수 | 용도 |
| --- | --- |
| `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD` | Compose의 MySQL 계정 비밀번호 |
| `DB_URL`, `DB_USER`, `DB_PASSWORD` | API를 Compose 밖에서 실행할 때의 DB 연결 |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD` | 인증과 STARTTLS를 사용하는 SMTP 연결 |
| `MAIL_FROM` | 확인·재설정 메일 발신 주소 |
| `VERIFY_BASE_URL` | 실제 HTTPS 서비스 주소의 `/verify-email` 경로 |
| `TRUSTED_PROXY_CIDRS`, `REQUIRE_TRUSTED_PROXY` | API가 신뢰할 프록시 주소와 필수 여부 |
| `PORTAL_HTTP_PORT` | 로컬 Compose 프록시 포트. 기본값 8080 |
| `MAIL_RETRY_POLL_MS` | 발송 대기열 재시도 간격. 기본값 60000ms |
| `CHOIR_BOOTSTRAP_DB_PASSWORD` | 최초 운영진 지정 명령에만 일시 공급하는 DB 비밀번호 |

운영 주소에는 HTTPS를 적용하고 쿠키의 `HttpOnly`, `Secure`, `SameSite=Lax`를 유지합니다. 로컬 `localhost`의 Chromium은 HTTP에서도 `Secure` 쿠키를 저장할 수 있으므로, 로컬 브라우저 동작을 운영 TLS의 대체 근거로 삼지 않습니다. 배포 인그레스가 정해지면 신뢰 프록시 CIDR과 실제 접속 IP 전달·위조 차단을 그 토폴로지에서 다시 검증합니다. 현재 Nginx는 들어온 전달 IP 헤더를 TCP 연결 주소로 덮어씁니다. 상위 프록시를 추가한다면 사용자별 IP 제한을 다시 검증해야 합니다.

## 스키마와 최초 운영진

API 기동 시 Flyway가 `api/src/main/resources/db/migration/`의 마이그레이션을 순서대로 적용하고 JPA는 스키마를 검증합니다. 운영 DB는 적용 전에 일관된 백업을 만들고, 새 버전을 별도 환경에서 먼저 기동해 마이그레이션과 이전 데이터 조회를 확인합니다. 이미 적용된 V1~V7 파일은 수정하지 말고 새 버전 파일로 변경합니다.

첫 운영진은 일반 가입과 메일 확인을 마쳐 `APPROVAL_PENDING`인 검증된 계정으로 지정합니다. DB 접속 권한이 있는 관리자가 API 프로젝트에서 `gradlew.bat bootstrapAdmin --args="<JDBC URL> <DB 사용자> <검증된 이메일> ACTIVE"`를 실행합니다. 비밀번호는 콘솔 입력 또는 일시적인 `CHOIR_BOOTSTRAP_DB_PASSWORD` 환경 변수로 전달하고 명령 인자에는 쓰지 않습니다. 이 명령은 운영진이 이미 있으면 거절하며 공개 HTTP 경로에서는 실행할 수 없습니다. 지정 후 감사 기록과 해당 계정의 운영진 화면 접근을 확인합니다.

## 메일, 계정과 승인

API의 기본 SMTP 설정은 인증과 STARTTLS를 요구합니다. 발송 주소·도메인의 실제 송신과 수신을 운영 환경에서 확인합니다. 가입 신청·재설정 요청은 메일 발송 대기열에 접수되고 워커가 링크를 만들어 보냅니다. 발송 실패가 계속되면 `auth_mail_outbox`의 미완료 행과 재시도 시각을 확인하고 SMTP 연결을 복구합니다. 일회용 링크 원문은 DB에 저장하지 않습니다.

가입자는 이메일 확인 후에도 회원 자료를 볼 수 없습니다. 운영진은 보유한 명단과 신청자 정보를 대조한 뒤 활동 단원 또는 OB로 승인하거나 반려합니다. 학교 메일 확인만으로 합창단 소속을 판단하지 않습니다. 접근 해제는 기존 세션을 무효화합니다. 메일 확인 링크는 24시간, 비밀번호 재설정 링크는 30분 동안 한 번 사용할 수 있습니다. 세션 만료는 30분입니다. 로그인 실패는 이메일·IP별 15분에 5회, 재설정 요청은 주소·IP별 15분에 3회로 제한합니다.

## 행사와 출석 현장 대응

운영진은 행사 대상에 OB 포함 여부를 지정하고 출석 창을 엽니다. QR과 입력 코드는 10분 동안 유효하며 재발급하면 이전 값은 즉시 무효가 됩니다. 코드가 유출되었다면 같은 행사 창에서 QR·코드를 재발급하고 새 코드만 현장에 표시합니다. 출석 창 종료 뒤 당시 대상 스냅샷의 미출석 기록이 남습니다. 운영진 정정에는 이유를 입력하며 수행자·시각·이전 상태·변경 상태가 감사 기록에 저장됩니다. 출석 시도 제한은 계정당 1분에 10회, IP당 1분에 100회입니다.

## 백업과 복구

DB 백업에는 회원, 인증 토큰 해시·세션, 메일 발송 대기열, 행사·공지·출석, 출석 대상 스냅샷과 감사 기록이 모두 포함되어야 합니다. DB 계정과 백업 파일의 접근 권한을 제한하고 암호화된 저장소에 보관합니다. 복구는 격리 환경에서 먼저 수행해 Flyway 버전과 핵심 테이블의 행 수, 회원 로그인 및 과거 출석 조회를 점검합니다. 운영 복구 시에는 API 쓰기를 중지하고 확인된 백업 시점과 복구 후 변경분 처리 방안을 운영진과 정한 뒤 진행합니다.

## 로컬 검증

API 통합 테스트는 Testcontainers MySQL을 사용합니다. 웹 단위 테스트·린트·빌드는 각각 `npm test -- --run`, `npm run lint`, `npm run build`로 실행합니다. `web/`에서 `npm run test:e2e`를 실행하면 전용 런처가 매번 새 Compose 프로젝트명과 DB 비밀번호를 만들고, 사용 가능한 루프백 포트와 별도 내부 네트워크를 선택합니다. 별도 DB 볼륨과 Mailpit에서 실제 브라우저로 가입부터 정정까지 검사한 뒤 자기 프로젝트 자원만 확인해 정리합니다. Playwright를 직접 실행하면 격리 식별자가 없어 시작하지 않습니다. E2E용 메일 설정은 `deployment/application-e2e.yaml`에만 있고 운영 API 기본 설정에는 적용되지 않습니다.
웹 개발 서버만 단독으로 실행하면 `/api/v1`이 연결되지 않습니다. API를 포함한 흐름은 같은 출처의 Compose Nginx 프록시를 통해 확인합니다.
